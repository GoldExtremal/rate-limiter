# Rate Limiter

Распределённый ограничитель частоты запросов: лимит на `client_id` (по умолчанию
100 запросов за скользящие 60 секунд), общий для нескольких инстансов FastAPI за
балансировщиком. Счётчики живут только в Redis, проверка и списание выполняются
одним Lua-скриптом. Индивидуальные лимиты клиентов хранятся в PostgreSQL.

```text
клиент → nginx :8080 (round-robin)
           ├── app1 (127.0.0.1:8001) ┐
           └── app2 (127.0.0.1:8002) ┴─→ Redis       счётчики
                                     └─→ PostgreSQL  лимиты клиентов, читаются на старте
```

## Запуск

Нужен только Docker (Engine 24+, Compose v2 — команда `docker compose`).

```bash
docker compose up --build
```

| Сервис | Адрес | Назначение |
| --- | --- | --- |
| nginx | `http://localhost:8080` | балансировщик перед app1 и app2 |
| app1 | `http://127.0.0.1:8001` | инстанс напрямую |
| app2 | `http://127.0.0.1:8002` | инстанс напрямую |

Миграции PostgreSQL применяются автоматически: одноразовый сервис `migrate`
отрабатывает до старта инстансов. Redis и PostgreSQL наружу не публикуются. Все внешние порты настраиваются через `APP_PORT`,
`APP1_PORT`, `APP2_PORT`; `.env` не обязателен — значения по умолчанию заданы в
`docker-compose.yml`, полный список переменных — в `.env.example`.

```bash
curl -s -X POST localhost:8080/check -H 'Content-Type: application/json' \
  -d '{"client_id": "user_123"}'
curl -si localhost:8080/demo -H 'X-Client-Id: user_123'
```

## API

### `POST /check`

```json
{"client_id": "user_123"}
```

```json
{"allowed": true, "remaining": 47, "reset_at": 1720000000}
```

- Всегда 200, решение — в поле `allowed`. При `allowed=false` дополнительно
  выставляется `Retry-After`.
- `client_id` — любая строка от 1 до 256 символов, иначе 422.
- `reset_at` — unix-время в секундах, когда освободится ближайший слот.

### `GET /demo`

Демо-эндпоинт под `RateLimitMiddleware`. Клиент определяется заголовком
`X-Client-Id` (UTF-8, 1–256 символов; иначе 400).

- Разрешено — ответ эндпоинта и заголовки `X-RateLimit-Limit`,
  `X-RateLimit-Remaining`, `X-RateLimit-Reset`.
- Превышено — 429 с теми же заголовками и `Retry-After`; эндпоинт не вызывается.

Лимит общий для `/check` и `/demo`: это два HTTP-контракта поверх одной проверки.

### `GET /health`

Liveness, всегда 200. На всех ответах есть `X-Instance-Id` — по нему видно, какой
инстанс ответил.

## Тесты

Все проверки выполняются в контейнерах внутри сети compose.

```bash
make check
```

| Цель | Что делает |
| --- | --- |
| `make up` / `make down` | поднять стенд и дождаться healthcheck / остановить и удалить данные |
| `make lint`, `make typecheck` | ruff и mypy |
| `make test-unit` | unit-тесты без внешних сервисов |
| `make test-integration` | приложение in-process против настоящих Redis и PostgreSQL |
| `make test-acceptance` | поднятые app1 и app2 через nginx и напрямую |
| `make test-acceptance-repeat` | приёмочные тесты 10 раз подряд |
| `make test` | все тесты, включая медленный тест восстановления после окна |
| `make check` | `lint typecheck test` |

Без `make`: `docker compose up -d --build --wait`, затем
`docker compose --profile test run --rm tests pytest tests/unit tests/integration tests/acceptance`.

Критерий приёмки проверяет `tests/acceptance/test_rate_limit.py`: 500
параллельных `POST /check` от одного `client_id` дают ровно 100
`allowed: true` — и через nginx, и при прямом распределении запросов поровну
между app1 и app2.

## Как это работает

### Скользящее окно по логу запросов

Ключ `rl:<client_id>` — sorted set: score — время запроса в миллисекундах по
часам Redis, member — случайные 8 байт (чтобы два запроса в одну миллисекунду не
схлопнулись в один). Скрипт `app/lua/sliding_window.lua`:

1. `TIME` — текущее время Redis в миллисекундах.
2. `ZREMRANGEBYSCORE key -inf (now-window` — удалить записи, вышедшие из окна.
3. `ZCARD key` — сколько запросов в окне.
4. Если меньше лимита — `ZADD key now member`, запрос разрешён; иначе ничего не
   пишется.
5. `ZRANGE` первой и последней записи — для `reset_at` и TTL.
6. `PEXPIRE key newest + window - now + 1`.

Решения и их причины:

- **Время только из Redis.** Часы инстансов могут расходиться, а `TIME` один на
  всех. Python-время в решении не участвует, `Retry-After` тоже считается в Lua.
- **Граница окна.** Запись со score `s` активна до `s + window` включительно,
  поэтому слот свободен с `oldest + window + 1` — это и есть `reset_at`.
- **TTL по новейшей записи, а не `PEXPIRE window` на каждый вызов.** Отказ не
  добавляет запись и не должен продлевать жизнь ключа. Ключ неактивного клиента
  исчезает ровно тогда, когда его последняя запись выходит из окна.
- **`limit = 0`** — отказ без единой записи, ключ не создаётся.
- **`#!lua`** в первой строке — объявление скрипта с флагами (Redis 7+), а не
  комментарий. Без флага `allow-oom` Redis отклоняет такой скрипт при нехватке
  памяти до выполнения, а не роняет его на `ZADD` после удаления старых записей.
- **Лимит не входит в ключ**: при смене лимита клиента история его запросов
  сохраняется.

### Атомарность

Вся проверка — один скрипт, вызываемый через `EVALSHA` (`register_script`;
при `NOSCRIPT` после рестарта Redis клиент сам загружает скрипт заново).
Redis исполняет скрипт целиком в однопоточном цикле команд: пока скрипт не
закончился, ни одна команда другого клиента — в том числе другого инстанса —
не выполнится. Поэтому два конкурентных запроса не могут оба увидеть 99 записей и
оба добавить сотую.

### Redis

- `noeviction`: при нехватке памяти политика вытеснения молча удалила бы ключ
  активного клиента и обнулила его счётчик. С `noeviction` Redis отклоняет запись
  ошибкой, лимит не превышается незаметно.
- Без персистентности: состояние живёт не дольше окна. Рестарт Redis даёт
  клиентам полный лимит заново.
- Память: sorted set до 128 элементов с короткими members хранится в компактной
  кодировке listpack, при лимите 100 это единицы килобайт на активного клиента.

### Индивидуальные лимиты в PostgreSQL

Задание называет PostgreSQL обязательной частью стека, но не говорит, что в нём
хранить. Принятое прочтение: Postgres — источник конфигурации индивидуальных
лимитов, то есть данных, которые меняют без передеплоя и которые должны быть
одинаковыми на всех инстансах. Счётчики по-прежнему только в Redis.

- Таблица `client_limits (client_id, rate_limit, updated_at)`; клиенты без строки
  получают `RATE_LIMIT`. `rate_limit = 0` блокирует клиента.
- Миграции — SQL-файлы в `migrations/`, свой runner на `asyncpg` с
  `pg_advisory_lock` (безопасен при параллельном запуске) и таблицей
  `schema_migrations`. Alembic потребовал бы SQLAlchemy ради одной таблицы.
- Seed из `SEED_CLIENT_LIMITS` (по умолчанию `client-a: 500`, `client-b: 50`,
  `client-c: 1000`) выполняется при каждом `up` с `ON CONFLICT DO NOTHING`:
  ручные правки в базе не откатываются.
- Каждый инстанс читает таблицу один раз на старте в неизменяемый снимок в
  памяти; горячий путь в Postgres не ходит. Если база недоступна, инстанс
  стартует со значениями по умолчанию и пишет warning, `/health` показывает
  `limits_loaded: false`.

Изменить лимит:

```bash
docker compose exec postgres psql -U ratelimiter -d ratelimiter \
  -c "INSERT INTO client_limits (client_id, rate_limit) VALUES ('user_123', 10)
      ON CONFLICT (client_id) DO UPDATE SET rate_limit = EXCLUDED.rate_limit, updated_at = now()"
docker compose restart app1 app2
```

Новый лимит применяется после рестарта инстансов; история запросов клиента в
Redis при этом сохраняется, потому что лимит не входит в ключ.

### Инстансы, пул и балансировщик

- Пул соединений Redis создаётся в lifespan и закрывается на shutdown. На старте
  выполняется `PING`; его неудача не роняет процесс.
- Одновременные обращения к Redis ограничены семафором размером с пул: иначе при
  всплеске запросов пул исчерпывается и redis-py бросает ошибку при живом Redis.
- nginx не повторяет `/check` и `/demo` на другом инстансе
  (`proxy_next_upstream off`): иначе один запрос клиента мог бы списаться дважды.
  Чтобы без повторов не было 502 после пересоздания контейнеров, nginx заново
  резолвит `app1`/`app2` через DNS Docker (`resolve`), а keepalive-таймаут
  uvicorn больше, чем у nginx.
- `X-Instance-Id` ставит внешняя ASGI-обёртка вокруг всего приложения — так
  заголовок есть даже на необработанном 500.
- `RateLimitMiddleware` — чистый ASGI, а не `BaseHTTPMiddleware`; `X-Client-Id`
  декодируется как UTF-8, чтобы кириллический id в `/demo` и в JSON `/check`
  попадал в один счётчик.

## Ответы на вопросы задания

**1. Что делает проверку атомарной?**

- Вся проверка — один Lua-скрипт:
  `TIME → ZREMRANGEBYSCORE → ZCARD → (ZADD) → ZRANGE → PEXPIRE`.
- Redis выполняет скрипт целиком, не переключаясь на команды других клиентов:
  между чтением счётчика (`ZCARD`) и списанием (`ZADD`) никто не вклинится.
- Раздельных `ZCARD`/`ZADD` из Python нет; время берётся из `TIME`, поэтому
  расхождение часов инстансов не влияет.

**2. Худший случай fixed window.**

- До 200 запросов за произвольные 60 секунд: 100 в последний момент одного окна и
  100 в первый момент следующего.
- Здесь используется sliding window по логу запросов: не более 100 за любые
  60 секунд.
