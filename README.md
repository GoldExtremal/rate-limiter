# Rate Limiter

Ограничение частоты запросов для нескольких инстансов FastAPI: **100 запросов за
любые 60 секунд на `client_id`**, общий счётчик в Redis, атомарная проверка
одним Lua-скриптом.

```text
               ┌──── app1 ────┐
клиент → nginx ┤              ├──→ Redis       счётчики (sliding window)
               └──── app2 ────┘ └─→ PostgreSQL  индивидуальные лимиты
```

## Быстрый старт

Нужен только Docker (Engine 24+, Compose v2).

```bash
docker compose up --build
```

```bash
curl -X POST localhost:8080/check -H 'Content-Type: application/json' -d '{"client_id": "user_123"}'
# {"allowed": true, "remaining": 99, "reset_at": 1720000060, "degraded": null}

curl -i localhost:8080/demo -H 'X-Client-Id: user_123'
# 200 + X-RateLimit-Limit / Remaining / Reset, после лимита — 429 + Retry-After
```

| Адрес | Что это |
| --- | --- |
| `localhost:8080` | nginx — балансировщик |
| `127.0.0.1:8001`, `:8002` | app1 и app2 напрямую, там же `/metrics` |

Порты меняются через `APP_PORT`, `APP1_PORT`, `APP2_PORT`. Все настройки — в
[`.env.example`](.env.example); `.env` не обязателен. Миграции применяются сами.

## API

| Метод | Что делает |
| --- | --- |
| `POST /check` | `{"client_id", "request_id"?}` → всегда 200, решение в `allowed` |
| `GET /demo` | закрыт лимитом по `X-Client-Id`: 200 или 429 с заголовками `X-RateLimit-*` и `Retry-After` |
| `GET /health` | всегда 200; состояние breaker и лимитов |
| `GET /metrics` | Prometheus, только на инстансах (в nginx закрыт) |

- `client_id` — любая строка 1–256 символов.
- `request_id` (`X-Request-Id` для `/demo`) — необязательный: повтор с тем же id не
  списывает второй слот.
- `degraded` — почему решение принято без ответа Redis: `redis_unavailable`,
  `redis_timeout`, `overloaded`; в штатном режиме `null`.

## Как это работает

**Скользящее окно.** Ключ `rl:<client_id>` — sorted set с временем запросов.
Один Lua-скрипт выполняет:

```text
TIME → ZREMRANGEBYSCORE (старые) → ZCARD → ZSCORE (повтор?) → ZADD (если есть место) → PEXPIRE
```

- Атомарно: Redis выполняет скрипт целиком, никто не вклинится между проверкой и
  списанием.
- Время берётся из Redis, поэтому часы инстансов не важны.
- TTL ставится по последней записи: ключ неактивного клиента исчезает сам.
- `noeviction`: при нехватке памяти Redis отклоняет запись, а не стирает чужие
  счётчики.

**Индивидуальные лимиты** лежат в таблице PostgreSQL `client_limits`. Инстансы
держат снимок в памяти и перечитывают его раз в 10 секунд — в Postgres на каждый
запрос не ходим.

**Отказы Redis:**

| Ситуация | `/check` | `/demo` |
| --- | --- | --- |
| Лимит превышен | `allowed: false` | 429 |
| Redis недоступен, fail-open (по умолчанию) | `allowed: true`, `degraded` | 200 без `X-RateLimit-*` |
| Redis недоступен, fail-closed | `allowed: false`, `degraded` | 503 |
| Одиночный таймаут или перегрузка | `allowed: false`, `degraded` | 503, `Retry-After: 1` |

- **Circuit breaker:** открывается после 5 ошибок соединения подряд или когда
  таймауты составляют больше половины вызовов за 10 секунд; через 5 секунд —
  одна проба.
- **Admission control:** не больше 64 одновременных обращений к Redis на инстанс;
  перегрузка всегда отклоняет запрос и никогда не включает fail-open.
- Ошибка в скрипте — 500, а не fail-open: баг не должен тихо выключать лимит.
- После возврата Redis всё восстанавливается само, без рестарта.

## Решения

| Выбрали | Вместо | Почему |
| --- | --- | --- |
| Sliding window (лог в ZSET) | fixed window, sliding counter | fixed пропускает до 200 за 60 с, counter приближённый |
| Один Lua-скрипт | `MULTI`/`WATCH`, раздельные команды | нет гонки между проверкой и списанием |
| Fail-open по умолчанию | fail-closed | отказ лимитера не должен ронять весь API |
| Таймаут при закрытом breaker — отказ | таймаут — fail-open | под нагрузкой лимит выключался бы при живом Redis (нашла нагрузка) |
| `noeviction` | вытеснение ключей | вытеснение молча обнуляет счётчик клиента |
| Лимиты в PostgreSQL | лимиты в env | это данные, а не конфигурация деплоя |
| nginx не повторяет `/check`, `/demo` | повтор на соседний инстанс | один запрос списался бы дважды |
| Свой breaker и admission | готовые библиотеки | мало кода, каждая строка объяснима |

Интерпретации задания:

- «`/check` всегда 200» — для валидного запроса; 422 на невалидный и 500 на баг
  остаются.
- PostgreSQL из общих требований хранит конфигурацию лимитов.
- `reset_at` — момент, когда освободится ближайший слот.
- `/check` — внутренний API: `client_id` берётся из запроса, аутентификация вне
  рамок задания.

## Нагрузка

**Условия.**

| | |
| --- | --- |
| Машина | AMD Ryzen 5 5500U (6 ядер / 12 потоков), 22 ГБ RAM, Ubuntu 24.04, Docker 29.1 |
| Ресурсы (`compose.load.yml`) | app1, app2, nginx, Redis — по 1 CPU; PostgreSQL — 0,5; Locust — 4 |
| Сервис | 2 инстанса × 1 воркер uvicorn, без `--reload` |
| Генератор | Locust, 4 процесса, через nginx |
| Данные | 10 000 обычных клиентов + 1 горячий (почти всегда отказ), 3 строки в `client_limits` |
| Прогон | прогрев 30 с, замер 120 с, перцентили, а не среднее |

**Устойчивая фаза** (150 пользователей × 10 RPS):

| RPS | Ошибки | p50 | p95 | p99 | degraded / shed |
| --- | --- | --- | --- | --- | --- |
| 1462 | 0 | 10 мс | 110 мс | 180 мс | 0 / 0 |

**Поиск насыщения** (`make load-saturation`):

| Цель, RPS | Факт, RPS | p95 | Вся проверка | Вызов Redis | degraded / shed |
| --- | --- | --- | --- | --- | --- |
| 1000 | 967 | 110 мс | 17 мс | 16 мс | 0 / 0 |
| 2000 | 1695 | 210 мс | 33 мс | 15 мс | 0 / 0 |
| 3000 | 2181 | 300 мс | 68 мс | 25 мс | 0 / 0 |
| 4000 | 2208 | 360 мс | 115 мс | 27 мс | 0 / 0 |
| 5000 | 2236 | 440 мс | 161 мс | 27 мс | 0 / 0 |

**Узкое место — CPU однопоточных инстансов, а не Redis:**

- Redis выполняет скрипт за **69 мкс** и загружен на ~25 %.
- Инстансы упираются в своё ядро; за точкой насыщения растёт очередь перед Redis
  (проверка 161 мс против 27 мс на вызов Redis).
- Ёмкость конфигурации — около 2200 RPS. Масштабируется добавлением инстансов:
  у Redis запас на порядок.
- Даже за точкой насыщения — ни одного деградированного решения: лимит под
  нагрузкой не выключается.

## Ответы на вопросы

**1. Что делает проверку атомарной?**
Вся проверка — один Lua-скрипт
(`TIME → ZREMRANGEBYSCORE → ZCARD → ZSCORE → ZADD → PEXPIRE`). Redis выполняет
скрипт целиком и не переключается на команды других клиентов, поэтому между
подсчётом и списанием никто не вклинится. Раздельных команд из Python нет.

**2. Худший случай fixed window?**
До **200** запросов за произвольные 60 секунд: 100 в конце одного окна и 100 в
начале следующего. Здесь sliding window — не больше 100 за любые 60 секунд.

**3. Redis недоступен 30 секунд — что видит клиент?**

- Остановленный Redis: через 5 ошибок соединения breaker открывается, дальше
  ответы мгновенные. По умолчанию (fail-open) клиента обслуживают без лимита:
  `allowed: true, degraded: "redis_unavailable"`. В fail-closed — `allowed: false`
  и 503 на `/demo`. Ни одного 429: сбой — не превышение лимита.
- Зависший Redis: запросы ждут не дольше 500 мс и отклоняются (`redis_timeout`),
  пока breaker не откроется по доле таймаутов.
- Раз в 5 секунд одна проба. После возврата Redis всё восстанавливается само,
  без рестарта; счётчики начинаются заново.
- Почему fail-open: лимитер защищает API, а не является бизнес-функцией, — его
  отказ не должен становиться отказом всего сервиса. Цена — на время сбоя строгой
  гарантии лимита нет; breaker и admission control её ограничивают.

## Что не сделано

- Аутентификация `/check` (`client_id` должен браться из токена).
- Высокая доступность Redis (Sentinel или Cluster — скрипт к Cluster готов).
- Мгновенное применение изменённых лимитов через `LISTEN/NOTIFY` вместо опроса
  раз в 10 секунд.
- JSON-логи и трассировка.
