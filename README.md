# Rate Limiter

Распределённый ограничитель частоты запросов: лимит на `client_id` (по умолчанию
100 запросов за скользящие 60 секунд), общий для нескольких инстансов FastAPI за
балансировщиком. Счётчики живут только в Redis, проверка и списание выполняются
одним Lua-скриптом. Индивидуальные лимиты клиентов хранятся в PostgreSQL.

```text
клиент → nginx :8080 (round-robin)
           ├── app1 (127.0.0.1:8001) ┐
           └── app2 (127.0.0.1:8002) ┴─→ Redis       счётчики
                                     └─→ PostgreSQL  лимиты клиентов, читаются на старте
```

## Запуск

Нужен только Docker (Engine 24+, Compose v2 — команда `docker compose`).

```bash
docker compose up --build
```

| Сервис | Адрес | Назначение |
| --- | --- | --- |
| nginx | `http://localhost:8080` | балансировщик перед app1 и app2 |
| app1 | `http://127.0.0.1:8001` | инстанс напрямую |
| app2 | `http://127.0.0.1:8002` | инстанс напрямую |

Миграции PostgreSQL применяются автоматически: одноразовый сервис `migrate`
отрабатывает до старта инстансов. Redis и PostgreSQL наружу не публикуются. Все
внешние порты настраиваются через `APP_PORT`, `APP1_PORT`, `APP2_PORT`; `.env` не
обязателен — значения по умолчанию заданы в `docker-compose.yml`, полный список
переменных — в `.env.example`. Пароль PostgreSQL `local-dev-only` — демо-значение
для изолированной сети compose, а не секрет.

```bash
curl -s -X POST localhost:8080/check -H 'Content-Type: application/json' \
  -d '{"client_id": "user_123"}'
curl -si localhost:8080/demo -H 'X-Client-Id: user_123'
```

## API

### `POST /check`

```json
{"client_id": "user_123"}
```

```json
{"allowed": true, "remaining": 47, "reset_at": 1720000000, "degraded": null}
```

- Всегда 200 для валидного запроса, решение — в поле `allowed`. При
  `allowed=false` дополнительно выставляется `Retry-After`.
- `degraded` — аддитивное поле: `null` в штатном режиме; `"redis_unavailable"`,
  `"redis_timeout"` или `"overloaded"`, если решение принято без ответа Redis
  (см. «Поведение при отказах»). Та же причина дублируется заголовком `X-RateLimit-Degraded`.
  `remaining` и `reset_at` в этом случае `null`: состояния лимита нет.
- Единственный не-200 для валидного запроса — 500 при программной ошибке
  (например, ключ клиента неверного типа): баг должен быть громким.
- `client_id` — любая строка от 1 до 256 символов, иначе 422.
- `reset_at` — unix-время в секундах, когда освободится ближайший слот.

### `GET /demo`

Демо-эндпоинт под `RateLimitMiddleware`. Клиент определяется заголовком
`X-Client-Id` (UTF-8, 1–256 символов; иначе 400).

- Разрешено — ответ эндпоинта и заголовки `X-RateLimit-Limit`,
  `X-RateLimit-Remaining`, `X-RateLimit-Reset`.
- Превышено — 429 с теми же заголовками и `Retry-After`; эндпоинт не вызывается.
- Redis недоступен: в fail-open эндпоинт вызывается без `X-RateLimit-*`
  (данных нет), в fail-closed — 503. При перегрузке или одиночном таймауте
  Redis — 503 и `Retry-After: 1`.
  Технический сбой никогда не даёт 429: 429 — утверждение о клиенте, а без
  Redis его сделать нельзя.

Лимит общий для `/check` и `/demo`: это два HTTP-контракта поверх одной проверки.

### `GET /health`

Liveness, всегда 200: недоступные Redis или PostgreSQL не делают инстанс
нездоровым — рестарт не лечит внешнюю зависимость. В теле — состояние breaker
и загрузки лимитов. На всех ответах есть `X-Instance-Id` — по нему видно, какой
инстанс ответил.

### `GET /metrics`

Метрики Prometheus. Через nginx закрыт (404): метрики снимаются с каждого
инстанса напрямую — `127.0.0.1:8001/metrics`, `127.0.0.1:8002/metrics`.

## Тесты

Все проверки выполняются в контейнерах внутри сети compose.

```bash
make check
```

| Цель | Что делает |

| `make up` / `make down` | поднять стенд и дождаться healthcheck / остановить и удалить данные |
| `make lint`, `make typecheck` | ruff и mypy |
| `make test-unit` | unit-тесты без внешних сервисов |
| `make test-integration` | приложение in-process против настоящих Redis и PostgreSQL |
| `make test-acceptance` | поднятые app1 и app2 через nginx и напрямую |
| `make test-acceptance-repeat` | приёмочные тесты 10 раз подряд |
| `make test-chaos` | остановка, зависание и OOM настоящего Redis |
| `make test` | все тесты, включая медленный тест восстановления после окна и chaos |

Без `make`: `docker compose up -d --build --wait`, затем

между app1 и app2.

## Как это работает

### Скользящее окно по логу запросов

Ключ `rl:<client_id>` — sorted set: score — время запроса в миллисекундах по
часам Redis, member — случайные 8 байт (чтобы два запроса в одну миллисекунду не
схлопнулись в один). Скрипт `app/lua/sliding_window.lua`:

1. `TIME` — текущее время Redis в миллисекундах.
2. `ZREMRANGEBYSCORE key -inf (now-window` — удалить записи, вышедшие из окна.
3. `ZCARD key` — сколько запросов в окне.
4. Если меньше лимита — `ZADD key now member`, запрос разрешён; иначе ничего не
   пишется.
5. `ZRANGE` первой и последней записи — для `reset_at` и TTL.
6. `PEXPIRE key newest + window - now + 1`.

Решения и их причины:

- **Время только из Redis.** Часы инстансов могут расходиться, а `TIME` один на
  всех. Python-время в решении не участвует, `Retry-After` тоже считается в Lua.
- **Граница окна.** Запись со score `s` активна до `s + window` включительно,
  поэтому слот свободен с `oldest + window + 1` — это и есть `reset_at`.
- **TTL по новейшей записи, а не `PEXPIRE window` на каждый вызов.** Отказ не
  добавляет запись и не должен продлевать жизнь ключа. Ключ неактивного клиента
  исчезает ровно тогда, когда его последняя запись выходит из окна.
- **`limit = 0`** — отказ без единой записи, ключ не создаётся.
- **`#!lua`** в первой строке — объявление скрипта с флагами (Redis 7+), а не
  комментарий. Без флага `allow-oom` Redis отклоняет такой скрипт при нехватке
  памяти до выполнения, а не роняет его на `ZADD` после удаления старых записей.
- **Лимит не входит в ключ**: при смене лимита клиента история его запросов
  сохраняется.

### Атомарность

Вся проверка — один скрипт, вызываемый через `EVALSHA` (`register_script`;
при `NOSCRIPT` после рестарта Redis клиент сам загружает скрипт заново).
Redis исполняет скрипт целиком в однопоточном цикле команд: пока скрипт не
закончился, ни одна команда другого клиента — в том числе другого инстанса —
не выполнится. Поэтому два конкурентных запроса не могут оба увидеть 99 записей и
оба добавить сотую.

### Redis

- `noeviction`: при нехватке памяти политика вытеснения молча удалила бы ключ
  активного клиента и обнулила его счётчик. С `noeviction` Redis отклоняет запись
  ошибкой, лимит не превышается незаметно.
- Без персистентности: состояние живёт не дольше окна. Рестарт Redis даёт
  клиентам полный лимит заново.
- Память: sorted set до 128 элементов с короткими members хранится в компактной
  кодировке listpack. Ключ клиента со 100 записями занимает 3,1 КБ
  (`MEMORY USAGE`), то есть `maxmemory 256mb` вмещает около 80 тысяч клиентов,
  одновременно исчерпавших лимит. Клиенты с лимитом больше 128 переходят на
  skiplist, это заметно дороже.

### Индивидуальные лимиты в PostgreSQL

Задание называет PostgreSQL обязательной частью стека, но не говорит, что в нём
хранить. Принятое прочтение: Postgres — источник конфигурации индивидуальных
лимитов, то есть данных, которые меняют без передеплоя и которые должны быть
одинаковыми на всех инстансах. Счётчики по-прежнему только в Redis.

- Таблица `client_limits (client_id, rate_limit, updated_at)`; клиенты без строки
  получают `RATE_LIMIT`. `rate_limit = 0` блокирует клиента.
- Миграции — SQL-файлы в `migrations/`, свой runner на `asyncpg` с
  `pg_advisory_lock` (безопасен при параллельном запуске) и таблицей
  `schema_migrations`. Alembic потребовал бы SQLAlchemy ради одной таблицы.
- Seed из `SEED_CLIENT_LIMITS` (по умолчанию `client-a: 500`, `client-b: 50`,
  `client-c: 1000`) выполняется при каждом `up` с `ON CONFLICT DO NOTHING`:
  ручные правки в базе не откатываются.
- Каждый инстанс читает таблицу один раз на старте в неизменяемый снимок в
  памяти; горячий путь в Postgres не ходит. Если база недоступна, инстанс
  стартует со значениями по умолчанию и пишет warning, `/health` показывает
  `limits_loaded: false`.

Изменить лимит:

```bash
docker compose exec postgres psql -U ratelimiter -d ratelimiter \
  -c "INSERT INTO client_limits (client_id, rate_limit) VALUES ('user_123', 10)
      ON CONFLICT (client_id) DO UPDATE SET rate_limit = EXCLUDED.rate_limit, updated_at = now()"
docker compose restart app1 app2
```

Новый лимит применяется после рестарта инстансов; история запросов клиента в
Redis при этом сохраняется, потому что лимит не входит в ключ.

### Инстансы, пул и балансировщик

- Пул соединений Redis создаётся в lifespan и закрывается на shutdown. На старте
  выполняется `PING`; его неудача не роняет процесс.
- Одновременные обращения к Redis ограничены семафором размером с пул: иначе при
  всплеске запросов пул исчерпывается и redis-py бросает ошибку при живом Redis.
  Ожидание слота ограничено по времени (см. «Поведение при отказах»).
- nginx не повторяет `/check` и `/demo` на другом инстансе
  (`proxy_next_upstream off`): иначе один запрос клиента мог бы списаться дважды.
  Чтобы без повторов не было 502 после пересоздания контейнеров, nginx заново
  резолвит `app1`/`app2` через DNS Docker (`resolve`), а keepalive-таймаут
  uvicorn больше, чем у nginx.
- `X-Instance-Id` ставит внешняя ASGI-обёртка вокруг всего приложения — так
  заголовок есть даже на необработанном 500.
- `RateLimitMiddleware` — чистый ASGI, а не `BaseHTTPMiddleware`; `X-Client-Id`
  декодируется как UTF-8, чтобы кириллический id в `/demo` и в JSON `/check`
  попадал в один счётчик.

### Поведение при отказах

**Классификация ошибок Redis.** Недоступностью считаются ошибки соединения,
таймауты, `OOM` и `READONLY` после failover. Любой другой `ResponseError`
(ошибка в скрипте, `WRONGTYPE`) — программная ошибка: 500, лог `error`, метрика
`ratelimit_script_errors_total`. Широкий `except RedisError` выдал бы баг за
отказ Redis и в fail-open молча выключил бы лимит навсегда.

**Режим при недоступности Redis** задаётся `FAIL_MODE_OPEN`:

| | `/check` | `/demo` |
| --- | --- | --- |
| fail-open (по умолчанию) | `allowed: true`, `degraded: "redis_unavailable"` | эндпоинт без `X-RateLimit-*` |
| fail-closed | `allowed: false`, `degraded: "redis_unavailable"` | 503, `Retry-After` при открытом breaker |
| одиночный таймаут, любой режим | `allowed: false`, `degraded: "redis_timeout"` | 503, `Retry-After: 1` |

Fail-open применяется только к подтверждённому отказу: ошибке соединения, `OOM`,
`READONLY` или открытому breaker. Одиночный таймаут при закрытом breaker
неотличим от перегрузки самого инстанса, а слот при этом мог успеть списаться,
поэтому такой запрос отклоняется. Это правило найдено нагрузочным тестом: на
насыщении (около 2300 RPS) перегруженный event loop обрабатывал ответы Redis
позже таймаута, и без него 136 запросов из 93 тысяч прошли в fail-open при
живом Redis. Настоящее зависание Redis даёт таймауты подряд — breaker
открывается, и дальше работает выбранный режим.

Почему fail-open по умолчанию: лимитер защищает публичный API от
злоупотреблений, а не является бизнес-функцией, и его отказ не должен
превращаться в отказ всего API для всех клиентов. **В fail-open режиме во время
недоступности Redis строгая гарантия rate limit временно теряется** — это
осознанная цена. Цена ограничена: breaker избавляет запросы от ожидания
таймаута, а admission control не даёт перегрузке выключить лимит. Fail-closed
реализован и протестирован для случаев, когда лимит защищает дорогой ресурс.

**Circuit breaker.** После 5 ошибок недоступности подряд breaker открывается,
и к Redis не обращаемся: решения деградации выдаются сразу. Через 5 секунд
ровно один запрос идёт пробой: успех закрывает breaker, ошибка открывает снова.
Методы breaker синхронные — проверка состояния, переход в HALF_OPEN и захват
пробы происходят без `await`, а в однопоточном event loop это атомарно, поэтому
блокировка не нужна. Отмена запроса или программная ошибка во время пробы её
освобождают, иначе breaker застрял бы в HALF_OPEN. Breaker хранит здоровье
зависимости, а не счётчики, и требование «счётчиков в памяти нет» не нарушает.

**Admission control: перегрузка — не отказ Redis.** Одновременных обращений к
Redis не больше размера пула, ожидание слота ограничено
`REDIS_QUEUE_TIMEOUT_MS`. Не дождались — `degraded: "overloaded"` с
`allowed: false` в любом режиме. Иначе во время атаки event loop захлёбывается,
вызовы Redis начинают таймаутить, и fail-open выключает лимит ровно тогда,
когда он нужнее всего. Следствие: пока Redis завис, а breaker ещё не открылся,
часть запросов получает `overloaded` или `redis_timeout` даже в fail-open —
проверить лимит нельзя, а перегрузка не должна его выключать.

**Таймауты** (`REDIS_TIMEOUT_MS=500`, `REDIS_QUEUE_TIMEOUT_MS=1000`) выбраны с
запасом: скрипт внутри сети Docker выполняется за доли миллисекунды, но 500
параллельных запросов на медленной машине (Docker Desktop, CI-раннер) не должны
превращаться в ложные отказы. Повторов поверх breaker нет. Таймаут не означает,
что скрипт не выполнился: ответ мог потеряться после списания слота — это
неустранимое свойство сетевого вызова, такие случаи видны как `kind="timeout"`.

**Старт без зависимостей.** Пул Redis и снимок лимитов создаются на старте, но
недоступность Redis или PostgreSQL не роняет процесс: Redis — ветка деградации
до первого успешного вызова, лимиты — значения по умолчанию.

### Метрики

| Метрика | Смысл |
| --- | --- |
| `ratelimit_decisions_total{outcome}` | `allowed`, `rejected`, `degraded_allowed`, `degraded_rejected`, `shed` |
| `ratelimit_check_duration_seconds` | вся проверка, включая ожидание слота |
| `ratelimit_redis_duration_seconds` | только вызов скрипта; разница с предыдущей — очередь admission |
| `ratelimit_redis_errors_total{kind}` | `connection`, `timeout`, `oom`, `readonly` |
| `ratelimit_script_errors_total` | программные ошибки Redis |
| `ratelimit_circuit_breaker_state` | 0 closed, 1 open, 2 half-open |
| `ratelimit_inflight_checks` | занятые слоты admission |
| `ratelimit_limits_loaded` | 1, если лимиты загружены из PostgreSQL |

`client_id` в метки не попадает: неограниченная кардинальность.

## Нагрузочный замер

```bash
make load
```

Locust в контейнере бьёт `POST /check` через nginx: 10 000 обычных клиентов и
один горячий клиент, который почти всегда получает отказ, — так нагружаются обе
ветки скрипта. Locust работает в нескольких процессах (`--processes -1`), разгон
30 секунд служит прогревом, после него статистика сбрасывается
(`--reset-stats`), измеряются следующие 120 секунд. Параметры: `LOAD_USERS`,
`LOAD_USER_RPS`, `LOAD_SPAWN_RATE`, `LOAD_RUN_TIME`. После замера Locust снимает
прирост метрик с обоих инстансов: замер валиден, только если среди решений нет
`degraded_*` и `shed`. В середине замера сохраняется `docker stats`. Отчёты —
в `load/reports/`.

| Латентность | p50 6 мс, p95 21 мс, p99 58 мс, max 201 мс |
| Решения | 182 203 allowed, 20 043 rejected, 0 degraded, 0 shed |
| Проверка в приложении | в среднем 3,4 мс, из них вызов Redis 3,3 мс |
| Скрипт на стороне Redis | 75 мкс на вызов (`INFO commandstats`) |
| CPU (`docker stats`) | app1 124 %, app2 122 %, nginx 45 %, Redis 30 %, Locust 124 % |

Разведочный прогон без ограничения темпа (400 пользователей) упирается примерно
в 2100–2300 RPS: медиана растёт до 110–160 мс, и почти всё время запроса —
ожидание в очереди admission.

### Узкое место

CPU однопоточных инстансов, а не Redis:

- Redis выполняет скрипт за 75 мкс и загружен на 30 %, а приложение видит тот же
  вызов за 3,3 мс — разница уходит на event loop и сетевой стек инстанса.
- app1 и app2 загружены на одно ядро каждый (сверх 100 % — системное время
  сетевого стека), на насыщении растёт именно очередь admission
  (`ratelimit_check_duration_seconds` против `ratelimit_redis_duration_seconds`).
- Генератор не упирался в CPU: 124 % при 12 доступных потоках.

Масштабирование — больше инстансов (или воркеров с multiprocess-режимом
метрик): Redis имеет запас на порядок. Оговорка: генератор и сервис делили одну
машину, абсолютные числа зависят от неё; соотношение «Redis против приложения»
от машины не зависит.

## Принятые решения и отвергнутые альтернативы

| Решение | Альтернатива | Почему отказались |
| --- | --- | --- |
| Sliding window по логу (ZSET) | fixed window | до 200 запросов за любые 60 с, нарушает лимит |
| | sliding window counter | O(1) памяти, но приближённый: может пропустить больше лимита |
| Один Lua-скрипт | `MULTI`/`WATCH` или раздельные команды | гонка между чтением и записью или повторы при конфликтах |
| Время из `TIME` Redis | время инстанса | часы инстансов расходятся |
| `noeviction` | `volatile-ttl`, `allkeys-lru` | вытеснение молча обнуляет счётчик клиента |
| Fail-open по умолчанию | fail-closed | отказ лимитера не должен ронять весь API; fail-closed доступен настройкой |
| Узкая классификация ошибок Redis | `except RedisError` | баг в скрипте выглядел бы как отказ Redis и выключал бы лимит |
| Таймаут при закрытом breaker — отказ | таймаут — fail-open | под нагрузкой лимит выключался бы при живом Redis (найдено нагрузкой) |
| Свой breaker и admission | `pybreaker`, `aiobreaker` | логика небольшая и должна объясняться построчно |
| Чистый ASGI middleware | `BaseHTTPMiddleware` | проблемы с contextvars и стримингом, лишний слой |
| Лимиты в PostgreSQL | лимиты в env | данные, а не конфигурация деплоя |
| Свой runner миграций | Alembic | потребовал бы SQLAlchemy ради одной таблицы |
| `client_id` из тела или заголовка | fallback на IP / `X-Forwarded-For` | за nginx IP клиента — IP nginx |
| Лимит не в ключе | `rl:<client_id>:<limit>` | смена лимита теряла бы историю запросов |
| `proxy_next_upstream off` для `/check`, `/demo` | повтор на соседний инстанс | двойное списание одного запроса |
| Свой алгоритм | `slowapi`, `fastapi-limiter`, `limits` | решают суть задания за нас |

Интерпретации задания:

- «`/check` всегда отвечает 200» — для валидного запроса в любом режиме
  лимитера; 422 на невалидный ввод и 500 на программную ошибку остаются.
- PostgreSQL обязателен по общим требованиям — используется как хранилище
  конфигурации лимитов (раздел выше).
- `reset_at` / `X-RateLimit-Reset` — момент, когда освободится ближайший слот:
  у скользящего окна нет единого момента сброса всей квоты.
- `/check` — внутренний API для доверенных сервисов: он принимает любой
  `client_id`, поэтому на публичном периметре `client_id` должен браться из
  аутентификации, а не из тела запроса. Аутентификация вне рамок задания.

## Сделал бы в продакшене

- Сервер Prometheus, дашборд и алерты на `shed`, `degraded_*` и состояние breaker.
- Высокую доступность Redis (Sentinel или Cluster — скрипт работает с одним
  ключом и к Cluster готов).
- Аутентификацию `/check` и `client_id` из токена.
- Структурированные JSON-логи, трассировку, read-only файловую систему
  контейнеров.
- Стандартизируемые заголовки `RateLimit` / `RateLimit-Policy` (IETF draft)
  рядом с `X-RateLimit-*`.
- Идемпотентность повторов `/check` по `request_id` клиента, чтобы повтор после
  потерянного ответа не списывал второй слот.
- Локальный приближённый лимит `limit / N_instances` на время отказа Redis —
  если требование «счётчиков в памяти нет» можно смягчить.

## Что не успели

- Breaker открывается по правилу «5 ошибок подряд». Лучше гибридное правило:
  доля ошибок за скользящее окно для таймаутов и «N подряд» только для ошибок
  соединения — оно ещё надёжнее отличает перегрузку от отказа.
- Лимиты из PostgreSQL читаются только на старте; нужно фоновое перечитывание с
  сохранением прежнего снимка при ошибке.
- Нагрузка снята одной устойчивой фазой; нет ступенчатого поиска точки
  насыщения.
- Chaos-тесты управляют Docker через socket; Toxiproxy позволил бы обойтись без
  него и добавить сквозной сценарий сетевой задержки.
- `mypy` работает без `--strict`.

## Ответы на вопросы задания

**1. Что делает проверку атомарной?**

- Вся проверка — один Lua-скрипт:
  `TIME → ZREMRANGEBYSCORE → ZCARD → (ZADD) → ZRANGE → PEXPIRE`.
- Redis выполняет скрипт целиком, не переключаясь на команды других клиентов:
  между чтением счётчика (`ZCARD`) и списанием (`ZADD`) никто не вклинится.
- Раздельных `ZCARD`/`ZADD` из Python нет; время берётся из `TIME`, поэтому
  расхождение часов инстансов не влияет.

**2. Худший случай fixed window.**

- До 200 запросов за произвольные 60 секунд: 100 в последний момент одного окна и
  100 в первый момент следующего.
- Здесь используется sliding window по логу запросов: не более 100 за любые
  60 секунд.

**3. Redis недоступен 30 секунд.**

- Первые 5 запросов на инстанс уходят в Redis. Остановленный Redis отвечает
  отказом соединения сразу, и к этим запросам уже применяется выбранный режим.
  Зависший отвечает таймаутом через 500 мс: такие запросы отклоняются как
  `redis_timeout`, а часть параллельных — как `overloaded`. После 5 ошибок
  подряд breaker открывается, и к Redis больше не обращаемся.
- Fail-open (по умолчанию): клиента обслуживают без лимита — `/check` отвечает
  `allowed: true, degraded: "redis_unavailable"`, `/demo` работает без
  `X-RateLimit-*`. Fail-closed: `/check` — `allowed: false`, `/demo` — мгновенный
  503 с `Retry-After`. Ни одного 429: технический сбой — не превышение лимита.
- Раз в 5 секунд одна проба. После возврата Redis проба закрывает breaker, пул
  переподключается, скрипт перезагружается по `NOSCRIPT` — рестарт приложения не
  нужен. Счётчики при рестарте Redis потеряны, клиенты получают полный лимит.
- Почему так: отказ лимитера не должен становиться отказом всего API, а
  деградация ограничена breaker и admission control (раздел «Поведение при
  отказах»). Поведение проверяют `tests/chaos`.
